# asset-pipeline · 设计表 → 规格 → 校验 → 入库

先读 `..\_shared\环境事实.md`。

## 一、先认清现状（2026-10-02 实测）

| 项 | 实测 |
|---|---|
| 设计表 | `D:\Godot4.7_Proj\squad-2d\解域游戏美术资产表.csv`：**54 条**资产，7 列（资产名/类别/规格/阵营/格式/**状态**/备注），UTF-8 **带 BOM** |
| 设计表 | `解域游戏动画帧规格.csv`：**25 条**动画，10 列（名称/分类/主体层/帧数/帧率·时长/循环方式/关键动作/尺寸px/共用范围/备注） |
| 工程实际资源 | `jieyu-1/assets/` **只有 2 个 PNG**（`maps/map_01_height.png`、`maps/map_demo_height.png`），都是高度图 |
| 状态分布 | `待制作` 51 / `待谈定` 2 / `已制作（程序生成起手稿）` **1** |
| 画面怎么来的 | **绝大多数是程序绘制**：`ui/HudBuilder.gd` 画几何、`ui/HudTextureFactory.gd` 程序生成贴图（`crosshair_arrow()` / `vignette()` 等） |

> ⚠ **最重要的一条**：本工程画面多为**程序生成**，不是 PNG 资产。
> 所以**绝对不要**看到「AI 画出来的东西显示了」就把资产表的状态改成「已制作」——
> 「程序画的」和「PNG 资产已完成」是两件完全不同的事（这条 `jieyu-progress-sync` 里也强调过）。

## 二、两个真问题（本轮实测发现，未修，交人拍板）

### 问题 1：资产表**没有可执行的标识**，动画表有
- 动画表第一列是 **`char_lower_idle`** 这种**纪律性 ID** —— 能直接用，能和代码/文件名对上。
- 资产表第一列是 **`角色-步枪兵`** 这种**人读描述** —— 无法映射到任何 `res://` 路径。
- 后果：校验无从下手，入库没有唯一键，重名/漏做无法自动发现。

**建议**：给资产表加一列 **`资源ID`**（kebab 或 snake，与动画表同风格），
例如 `char_rifleman_base`；真正的文件路径由 ID + 规格推出，而不是另写一列手工维护的路径。
这是**改设计表**，属于文档决策 —— 按 `jieyu-progress-sync` 的规矩登记进待拍板，不要自己拍。

### 问题 2：`规格` 列有 16 条**不可解析**，且有 1 组**近似重复**
`scripts/check_assets.py` 实测（2026-10-02，54 条规格）：

**无法解析成 `WxH` 的 16 条**：
```
按8.2几何(6)   按需(6)   按8.2炮塔(2)   半径10m(1)   椭圆(1)
```

**归一化后近似重复 1 组**（全角/半角括号，其实是同一条）：
```
64×64px(近战档)  vs  64×64px（近战档）
```

**建议**：`规格` 列只允许机器可解析的 `W×H` 形式；把「按需 / 按8.2几何 / 半径10m / 椭圆」这类
**移到备注列**。这是**改设计表**，同样登记待拍板。

> 对照：动画帧规格表的「尺寸px」列也有 3 行是 `—`、5 行是 `按 8.2 几何`，
> 但它至少 **25/25 的名称都是 snake_case**（校验器实测 `[OK]`）——资产表该向它看齐。

## 三、流水线四步

### 步骤 1 · 设计表（TARGET，不要被工程实况改写）
`解域游戏美术资产表.csv` / `解域游戏动画帧规格.csv` 是**设计目标**。
工程按切片实现是正常的 —— **不许**把「目标 25 把武器」改成「5 把」来消灭不一致（同 `jieyu-progress-sync` 铁律）。

### 步骤 2 · 资源规格（命名 / 目录 / 尺寸 / 帧数）
这是本技能真正要**固化**下来的东西：

| 类型 | 命名 | 目录 | 尺寸 |
|---|---|---|---|
| 角色俯视贴图 | `char_<兵种>_<动作>.png` | `res://assets/chars/` | 按规格列（现多为 `64×64`） |
| 角色动画帧序列 | `char_<兵种>_<动作>_<序号2位>.png` | `res://assets/chars/<兵种>/` | 同动画表 `尺寸px` |
| 载具 | `veh_<载具代号>_<部位>.png` | `res://assets/vehicles/` | 按 `8.2 几何` 算出 |
| 武器 | `wpn_<武器代号>.png` | `res://assets/weapons/` | 按规格列 |
| 地形高度图 | `map_<名称>_height.png` | `res://assets/maps/` | 见地图规格表 |

**命名硬规则**（新资产一律照此，别各写各的）：
1. 全小写 + 下划线；**不要中文文件名**（导出与跨平台最容易在这里出事）。
2. 用**动画表那种风格**的 ID（`char_lower_idle` 是正例，`角色-步枪兵` 是反例）。
3. 动画帧序号**补零两位**（`_01` … `_08`），否则排序会错。
4. **同名不同用途必须区分**（`_base` / `_hurt` / `_dead`），不要靠目录区分。
5. 尺寸进文件名的做法**只在设计表里用**；真实文件名**不带尺寸**（改了尺寸不用改名）。

### 步骤 3 · 校验（`scripts/check_assets.py`）
入库前跑一次，用它把「文档说 / 工程有」的差异**打出来**：

```powershell
$py = "D:\dsh-data\dsh-runtimes\dsh-primary-runtime\dependencies\python\python.exe"
& $py "D:\dsh-data\skills\asset-pipeline\scripts\check_assets.py" `
     --design "D:\Godot4.7_Proj\squad-2d" `
     --project "D:\Godot4.7_Proj\jieyu-1"
```

它检查并报告：
1. **状态 vs 实际**：状态为「已制作」的，工程里能否找到对应资源（**并明确区分「程序生成」与「PNG 文件」**）。
2. **规格可解析性**：`规格` 列里无法解析成 `W×H` 的条目（`按需`/`按8.2几何`/`半径10m`…）列出来。
3. **近似重复**：忽略全角/半角括号与空白后**归一化相同**的规格值（就是上面那组）。
4. **工程里有无命名违规**：`res://assets/` 下的文件名是否含中文 / 大写 / 缺补零序号。
5. **孤儿资源**：工程里有、但设计表里找不到对应的 PNG（可能是临时产物或漏登记）。
6. **BOM / 列数**：CSV 是否仍是 UTF-8 **带 BOM**、列数是否被改动。

退出码：`0` = 没发现问题；`1` = 有需要处理的发现（**不等于失败**，是给人看的清单）。

### 步骤 4 · 入库
- 放进 `res://assets/<类别>/`，文件名按步骤 2。
- **Godot 的 `.import` 文件要一起进版本库**（它是导入设置，不是缓存）。
- 本项目纹理过滤是 **Nearest**（`default_texture_filter=0`）——像素风资产**不要**做抗锯齿/插值，否则糊。
- 改完 **跑一次测试**（`--headless --script res://tools/run_tests_headless.gd`），
  确认没有脚本因为资源路径变化而红。
- **然后**才更新设计表的 `状态` 列（而且只更新真的以 PNG 形式入库的那些）。

## 四、铁律

1. **程序生成的 ≠ PNG 资产已完成。** `HudBuilder` 画出来的几何体、`HudTextureFactory` 生成的贴图，
   都不算「资产表里的 PNG 已制作」。这是本技能最容易犯的错。
2. **设计表是 TARGET，不许按工程现状改小。** 不一致本身就是要报告的信息。
3. **CSV 必须保持 UTF-8（带 BOM）与列数**；改完要回读校验。
4. **中文文件名不要进 `res://`**（跨平台导出风险）。
5. **`状态` 列是唯一日常跟着工程走的列**，改它要有依据（文件真的存在且已入库）。
6. 改设计表结构（比如加 `资源ID` 列）属于**文档决策** → 登记待拍板，别自己拍。
7. 入库后**必须跑测试**，别让资源改名悄悄打断脚本。

## 五、脚本

| 脚本 | 作用 |
|---|---|
| `scripts/check_assets.py` | 读两张设计表 + 扫工程 `assets/`，报告状态/规格/重复/命名/孤儿/BOM 六类差异 |

只依赖标准库（`csv` / `re` / `struct` / `pathlib`），不依赖 Pillow（PNG 尺寸直接读文件头）。
