# 《解域》地图数据规格补充（jieyu_map 插件引入的扩展字段）

> 本文只记录**超出 `解域游戏.docx` 12.8 已定稿内容**的部分，供「要不要把这些补进正式文档」拍板。
> 已定稿的字段一律照抄，没有改动：本文提到的一切实现在
> `addons/jieyu_map/core/JieyuMapSpec.gd` 里都有对应常量与出处注释。

---

## 一、目录结构：与 12.8.1 的差异

12.8.1 写的是 `Maps/<map_id>/`（引擎无关的抽象路径）。
本工程落在 **`res://assets/maps/<map_id>/`**，理由是工程现有的自制高度图约定（`GameConfig.MAP_HEIGHT_DIR`）就在这里，
且 `Main.map_height_image` 指向 `res://assets/maps/*.png`。

同时**额外产出**一份 `<map_id>_height.png`（单张扁平高度图，放在 `assets/maps/` 根下）——
这是为了让工具链产出的图**不改任何工程代码就能试跑**（直接把 `map_height_image` 指过去）。

## 二、新增：内容层（4.17 环境互动区的图上标注）

12.8.1 的六份文件里没有「环境互动区」这一项，而 4.17（泥泞 / 雪地 / 草丛）需要空间数据。
工程现状是 `MapGenerator.demo_terrain_zones()` 硬编码三片圆形区域。

**插件新增两张可选图**（在 `meta.json` 的 `content_layers` 字段里声明；没有这两张图时工程应静默跳过）：

| 文件 | 格式 | 语义 |
|---|---|---|
| `content.png` | RGB8，1000×1000 | **行序方案**：第 N 行 = 第 N 片区域；同一片区域内必须纯色。颜色→kind：`(107,82,51)` 泥泞 / `(240,245,255)` 雪地 / `(61,133,61)` 草丛 |
| `material.png` | L8，1000×1000 | **材质 id 图**：0 = 无，1 = 泥泞，2 = 雪地，3 = 草丛 |

`meta.json` 里的声明：

```json
"content_layers": {
  "name": "terrain_content",
  "rows_file": "content.png",
  "material_file": "material.png",
  "merge_mode": "max_conceal"
}
```

> `merge_mode` 的口径与 `systems/terrain/TerrainZones.gd` 一致：速度取**最慢**、隐蔽取**最强**并封顶
> `GameConfig.TERRAIN_CONCEAL_MAX`。两张图给的是同一份数据的两种表达，**任选一张**即可；
> 两者同时存在时以 `material.png` 为准。

**落地状态（2026-10-04 复核）**：工程侧**已经读了** —— `WorldSetup._terrain_zone_entries()` 读地图**根目录**的
`material.png`，转成 TerrainZone 列表；`TerrainZones` 的纯查询层一行没改。

但复核时发现它其实**从第四十九版起就没生效过**：`JieyuMapDoc.save()` 里「把内容材质图另存到地图根目录」
那段写在 `payload is Image` 分支的 `continue` 之后，而 `content_material` 恰恰是 Image ⇒ **根目录的
`material.png` 从来没被写出来过**（`grassland_demo2` 也缺，2026-10-04 已补）。于是工程侧每次都在
`FileAccess.file_exists()` 那一步返回、静默退回 `MapGenerator.demo_terrain_zones()` 的三片摆位 ——
「图里标了内容层」与「游戏里真有内容层」之间是断的。现已修复，并把「根目录有图 + 读得到内容层」
写进 `test/jieyu_map_test.gd`。工程侧的读法同时改成与高度图同一条「ResourceLoader 优先」，
否则导出包里 PNG 变成 `.ctex`、`Image.load_from_file(res://…)` 读不到。

**仍需拍板的两点**：① `meta.content_layers.rows_file / material_file` 声明的是根目录文件名，而工作层草稿
另存在 `layers/`（`content_rows.png` / `content_material.png`）—— 两套名字要不要统一；
② 内容层只用「等面积圆」表达（`terrain_zones_from_material_image`），长条区域会被近似成圆饼，
要不要改成多边形 / 逐格查询。

## 三、新增：`meta.json` 扩展字段
12.8.7 的 meta 字段全部保留，插件额外写了四个键（**工程侧不读也不影响运行**）：

| 字段 | 用途 |
|---|---|
| `content_layers` | 见第二节 |
| `content_counts` | `[泥泞格数, 雪地格数, 草丛格数]`，供人一眼看内容层规模 |
| `roads` | `[{name, path[[x,y]…], width_m}]`：12.8.1 没有单独的道路文件，插件把道路折线记在这里（道路的**地形效果**已经烘进高度图，这份记录只用于重生成与审阅） |
| `recipe` | 生成配方回执（seed / grid / node_count / 河谷参数 / generator），保证「这张图是怎么来的」可复现 |

## 三点五、「哪些东西能摧毁」在数据里怎么表达（文档现状与插件口径）

**文档现状（原样核对过 `解域游戏.docx` 全文）**：

- `occluders.json` 每项有 `destructible` 与 `hp`（标「可选」）⇒ **判据只有这一个布尔字段**；
- 有明文耐久的只有**沙袋**：4.17 / 20.5「轴对齐矩形沙袋（7.2 × 2.2 m、顶高 1.1 m、**耐久 200**）、
  只挡通视与子弹、不阻挡人员通行；可破坏 —— 耐久清零后退出 occluder 组」；
- 建筑只有**思路**（4.17「可破坏掩体（建筑）的毁伤沿用 8.2.6 的载具毁伤思路（部位 + 血量）」），
  没有血量、没有部位、没有破坏后的地形/通行变化；
- 文档**自己承认这个缺口**：21.2.2 ⑧「建筑毁伤规则：多处提『建筑毁伤更多』，
  但只有载具（8.2.6）与沙袋（20.5 工程侧）有血量，建筑本身没有毁伤判定」；
- 第一版范围（22.10）把**建筑毁伤**明确降级为「后续版本」。

**插件据此定的口径**（`JieyuMapGen` / `JieyuMapChecks`）：

| 物件 | 插件写什么 | 依据 |
|---|---|---|
| 建筑（building） | `destructible: true` + `hp`（按占地分档）+ 三段 `damage_profiles` | 2026-10-03 拍板①（见三点六） |
| 半高墙 / 沙袋（wall） | `destructible: true` + `hp: 200` + 三段 `damage_profiles` | 4.17 / 20.5 的沙袋耐久，与工程 `GameConfig.COVER_HP` 同值 |
| 地形（高程） | 不参与可摧毁性 | 12.2 补充：1 m 高程网格承担全部**静态**地形与固定掩体 |

校验器两条：`destructible=true` 却没有 `hp`（WARN）、三段阈值表缺行或比例越界（ERROR）。

| # | 拍板 | 落地位置 |
|---|---|---|
| ① | **遮挡体一律可摧毁**（`destructible = true`） | `JieyuMapSpec.DEFAULT_DESTRUCTIBLE`；`JieyuMapGen.place_settlements` / `JieyuMapPainter.add_occluder` 的默认值 |
| ② | **建筑结构值锚点「标准档 1200」**（与 FOB 同档）；伤害按**弹药类别**分档，普通子弹为 0 | `JieyuMapGen.building_hp_for_footprint()`；`data/weapons_data.txt` 的 `structure_damage` 列；`data/vehicles_data.txt` 的 `gun_structure_damage` / `atgm_structure_damage` 列 |
| ③ | **破坏后留贴地残痕 + 小减速，不影响通视** | `entities/zone/RubblePatch.gd`（与泥泞共用移速链路）；摧毁段的 `rubble` 声明 |

| 弹药类别 | 武器 | 对建筑伤害 | 拆一栋 1200 需要 |
|---|---|---|---|

| .50 反器材 | m107barrettm82 | 55 | 21.8 发 |
| 40mm 榴弹 | m320 | 90 | 13.3 发 |
| 单兵反坦克火箭 | at4rpg7 | 600 | **2 发** |
| 单兵反坦克导弹 | 12javelin | 800 | **1.5 发** |
| 12.7mm 车装机枪 | apc_apcb / apc_apcd / veh_18 | 30 / 30 / 20 | 40 / 40 / 60 发 |
| 25 / 30mm 机炮 | ifv_ifvb / ifv_ifvc / ifv_a / heli_* | 35 / 35 / 45 / 45–50 | 26.7–34.3 发 |

> 口径说明：`structure_damage` **缺列或空串 ⇒ 0（打不动）**，不是「能打」——
> 默认值必须落在「普通子弹打不动建筑」这一侧（`WeaponTable.DEFAULT_STRUCTURE_DAMAGE = 0`）。
> 一栋标准建筑要 4–5 发主炮或 2 发火箭，工程意义是**拆楼是重武器的活，不是步枪的活**。

**④ 的阈值表形态**（`occluders.json` 每条可摧毁物一行）：

```json
"damage_profiles": [
  { "state": "intact",    "damaged_below_ratio": 0.70, "height_scale": 1.00, "blocks_sight": true },
  { "state": "damaged",   "damaged_below_ratio": 0.00, "height_scale": 0.45, "blocks_sight": true },
  { "state": "destroyed", "damaged_below_ratio": -1.0, "height_scale": 0.00, "blocks_sight": false,
    "rubble": { "material_id": 4, "radius_scale": 1.25, "speed_scale": 0.70 } }
]
```

- 建筑的受损 `height_scale` 取 **0.60**（比沙袋的 0.45 保守：楼塌一半不该比沙袋还矮）。
- 受损档的物理含义只是「挡视线的缝变大」：通视与子弹都走 `top_height_at()`，
  沙袋顶高从 1.1 m 掉到 0.495 m ⇒ 越过它所需的视线高度整整降 0.605 m。
  **0.495 m 仍落在文档 4.6 的「矮掩体 0.5–2 m」档里**，所以卧姿仍越不过去 —— 受损不等于消失。
- 工程侧读法：`Cover.is_damaged()` / `height_scale()` / `effective_height()` 已把三段折进现有接口，
  `SightSystem` 与 `BallisticsSystem` **一行都不用改**（它们只问 `top_height_at()`）。
- 残痕用的 `material_id = 4` 是 `material.png` 的新增取值；工程侧
  `MapGenerator.terrain_zones_from_material_image()` 解析时**跳过 4**（残痕由摧毁时现落，不从图里读）。

**第三轮已补上（见三点八）**：结算调用点已经接好了 —— 直射、间瞄、车载三条路都落到
`Cover.take_structure_damage()` 上。剩下的欠账只剩「工程兵 C4 / TNT 实体还没建」。

## 三点七、建筑可命中体积：窗 / 门洞（2026-10-03 第二轮拍板）

第一轮把「建筑可摧毁」定下来之后，紧接着要回答的是**一发炮弹怎么才算打中这栋建筑**。
使用者的选择：**按窗 / 门洞算 —— 只有打中开口才能伤到里面**，且**开口可穿透**
（打中开口也就能打到屋子里的单位）。

### 数据（12.8.7 的新增字段）

`occluders.json` 每条遮挡体多一个 `openings[]`（窗 / 门洞都在这里，不另开文件）：

```json
"openings": [
  { "type": "window", "center": [0.0, -5.0], "half_size": [1.2, 0.6], "h_low": 0.75, "h_top": 0.0 },
  { "type": "door",   "center": [0.0,  5.0], "half_size": [1.0, 0.6], "h_low": 0.0,  "h_top": 0.0 }
]
```

| 字段 | 口径 |
|---|---|
| `type` | `window` / `door`（只有这两种） |
| `center` / `half_size` | **本地坐标**（与 polygon 包围盒中心同一个坐标系），随遮挡体旋转一起转；`half_size` 里较大的那一轴沿墙展开、较小的那一轴跨墙厚 |
| `h_low` / `h_top` | **相对地面**的高度区间；`h_top = 0` 是约定值「到掩体顶」 |
| 默认尺寸 | 窗：宽 2.4 m、窗台 **0.75 m**；门：宽 2.0 m、落地到顶；跨墙厚 1.2 m |

**为什么窗台取 0.75 m**：它落在卧姿眼高 0.6 m 与站姿眼高 1.6 m 之间，
于是「站姿能透过窗看到屋里、卧姿看不到」是一条干净的边界（与 C2 矮掩体同一套直觉）。

### 判定与穿透（工程实现口径）

判定入口是 `SightSystem.cover_blocks()`（**静态纯判定**，可单测）；`occluder_blocks()` 只是遍历组调它。

1. **入口高度** = 线段与遮挡体矩形的第一个几何交点处的视线高度（相对地面）
2. 该交点落在某个开口格内、**且高度落在开口区间里** ⇒ 从开口穿过去
3. 穿过入口之后继续找**第一个非开口交点**：
   - 找到 ⇒ 停在那里（**对侧墙**就是结构伤害的落点，入口那面墙不吃「直射穿窗」的伤害）
   - 找不到（整条线都从开口过）⇒ 不挡（看得见 / 打得进）
4. 高度不够（卧姿低于窗台 0.75 m）⇒ 入口就是实心墙 ⇒ 挡住

**既有链路一行都没改**：`SightSystem.first_cover()` 与 `BallisticsSystem.resolve_shot()` 只是调用方；
开口口径收在 `Cover.segment_hit(from, to, sight_height)` 里，
`Cover.far_wall_hit()` 供结构伤害取落点，`Cover.wall_hit(..., include_openings=false)` 供取入口几何。

### 谁来放开口

**编辑器插件**：dock 新增「放窗 / 放门 / 删开口」三个工具（就近吸附到最近的一面墙）；
生成器给每栋新建筑默认**一窗一门**（摆在较长的那一对边的中段），
半高墙默认留一条缝（4.6 铁律：核心区建筑不能完全封闭、必须留有暴露面）。

### 校验规则（新增六条）

| 判据 | 级别 |
|---|---|
| 建筑一个开口都没有（打不进、也看不见里面） | WARN |
| 建筑开口数 < 2（六章：每个占领点 3 个以上入口/射击窗） | WARN |
| `type` 不是 window / door | ERROR |
| 开口没贴在墙面上（悬空的洞，弹道判据形同虚设） | WARN |
| `half_size` 非正 / `h_low < 0` / `h_top < h_low` / `h_top` 高过掩体顶 | ERROR |
| 窗但窗台高为 0（等于落地窗 / 门） | WARN |

### 炸弹不吃开口规则

- **间瞄炮击**（155mm 榴弹炮 / 迫击炮）走落点圈：按「落点圈 ∩ footprint」结算，不看开口。
- **炸药**（C4 / TNT）只看贴在哪个 footprint 上，不看开口。
- 开口只约束**直射**弹道 —— 也就是说「这栋楼有没有窗」不影响炮击与爆破拆楼。

## 四、新增：12.8.8 待确认项的口径选择

12.8.8 第 ④ 条写着「Occluder 与 zones 的标注方式（编辑器插件 vs 手写 JSON）」——
**本轮选定：编辑器插件 + 无头 CLI 双入口**，理由：

- 手写 JSON 的致命问题是**没有校验**：核心区里塞建筑、进入通道只写 1 条、节点间距 80 m，
  这些在 JSON 里都是合法数据，但会让地图不可玩（4.2 / 六章）。
- 因此插件的重点不是「画得快」，而是**画的时候就告诉你哪条铁律破了**：
  `JieyuMapChecks` 把六章能机器判的指标全部落成断言，`validate` 有 ERROR 就退出码 1。
- agent 走 CLI（可脚本化、可批处理、退出码可判），人走 dock（所见即所得）。

12.8.8 第 ③ 条「导航网格方案」**仍未决**：因此校验器里
「侧翼绕后路径 ≤ 正面 ×1.5」只给 INFO 提示，不编造数字。

12.8.8 第 ⑤ 条「载具坡度通行阈值」当前取 `GameConfig.MAX_SLOPE_DEG`（30°，12.8.5 的候选值已落成常量）；
插件的道路画笔另有更严的 `CORRIDOR_FLAT_DEG`（8°）用于「这段路能跑车」的局部判据。

## 五、验证器采用的通视口径（与工程一致性声明）

校验器里的通视判定（`JieyuMapChecks._is_open_line`）与工程 `SightSystem` 保持同一条数学内核：

- 采样：1 m 网格 + 双线性插值；容差 `GameConfig.SIGHT_MARGIN`（0.3 m）
- 眼高：`GameConfig.SOLDIER_EYE_HEIGHT`（1.6 m）
- 判据：视线高度 < 地形高度 + 容差 ⇒ 被挡（与 `systems/terrain/SightSystem.gd` 的地形层一致）

**差异（有意为之）**：校验器不读 `Occluder` 场景节点，而是用自己的「有掩体采样格」（多边形 + 5 m 缓冲）。
理由是校验发生在**还没有实例化场景**的时候；代价是它比运行时的三级通视**更保守**（更容易判"挡"）。
如果将来要逐点复验，用 `Main` 的 `map_preview_mode` 走 `MapPreview` 探针即可。

## 三点八、谁能扣建筑的结构值（2026-10-03 第三轮拍板）

第二轮把「可命中体积」定成窗 / 门洞之后，剩下的是「谁有资格扣这座楼的血」。
使用者的选择：**给 `resolve_shot` 加一个弹种参数**（让弹道系统仍不懂武器）、
**三类伤害源一次做完**、**同一套三段 + 两套血量入口**、**开口不做逐条状态**。

### 两套血量入口（同一套三段状态机）

| 物件 | 血量 | 谁扣得动 | 数据字段 |
|---|---|---|---|
| 沙袋 / 半高墙 | 掩体耐久 **200** | **子弹伤害**（近距 62 ⇒ 4 发打坏，保留老手感） | `hp: 200` + `absorbs_bullets: true` |
| 建筑 | 结构值 **800 / 1200 / 3000** | **弹种口径的结构伤害**（普通子弹恒为 0） | `hp: 1200` + `absorbs_bullets: false` |

两套入口最终都落到同一个 `Cover._apply_damage()` ⇒ 三段阈值（`damage_profiles`）与摧毁后的
残痕 / 退出 occluder 组行为完全一致，不需要维护两份状态机。

`absorbs_bullets: false` 是 `occluders.json` 的新字段（2026-10-03 第三轮加）：
它把「普通子弹对建筑伤害恒为 0」这条规则**写进数据**，而不是靠代码里 if 判断物件类型 ——
以后要加「钢制哨塔（吃子弹但结构值高）」这种中间态，只改数据。

### `resolve_shot()` 的新参数

```gdscript
static func resolve_shot(origin, direction, max_range, enemies, hit_radius,
        sight, shooter_eye_height, structure_damage := -1.0) -> Dictionary
```

返回的字典多一个 `structure_damage`（已被 clamp 到 ≥ 0），结算方不必再查一次表。
**-1 = 走缺省 0**，也就是「不传就拆不了楼」—— 默认值落在**安全的那一侧**，
漏传参数不会悄悄把楼拆掉。

### 三条已接好的链路

| 谁 | 结构伤害来源 | 结算处 |
|---|---|---|
| 玩家步兵 | `WeaponTable` 的 `structure_damage` 列（按当前武器）；普通子弹 = 0 | `Main._on_player_fired()` |
| 敌方步兵 / 队友 | `Enemy.structure_damage` 导出属性（步兵 = 0，将来给重武器敌人设值） | `Enemy._fire()` / `Ally._fire()` |
| 玩家 / 敌方载具 | `VehicleTable` 的 `gun_structure_damage` / `atgm_structure_damage`（按当前弹种） | `VehicleController` / `Vehicle._fire_ai()` |
| 间瞄炮击 | `IndirectFire.structure_damage`（`IndirectController` 灌 `GameConfig.INDIRECT_STRUCTURE_DAMAGE` = 420） | `IndirectFire._explode()` |

**间瞄与直射是两套口径**（拍板时有意为之）：
直射必须打中窗 / 门洞才伤得到里面；间瞄按「落点圈 ∩ footprint」+ `structure_blast_at()` 衰减结算，
**不看开口** —— 炮弹不管门窗。爆心给满、半径处衰减到 35%（`GameConfig.BLAST_STRUCTURE_FALLOFF`），
取 0.35 而不是对人那档的 0.28：炮击本身有 10 m 半径散布，衰减太狠会让「打偏一点就毫无意义」。

## 三点十、出生区（spawn_areas）也读地图了 —— 但**出生点不能取质心**（2026-10-05 第六十一版）

`zones.json` 只给出生区**多边形**，不给出生点。最省事的做法是取质心，实测**不行**：

| 位置 | 双尺度坡度 | 结论 |
|---|---|---|
| demo 出生点 (50, 500) | step8 20.2° / step4 **45.8°** | 河岸，站不住 |
| west 出生区质心 (85, 500) | step8 **61.5°** / step4 **60.5°** | 更糟 |
| 挑出来的点 (122, 655) | 0.0° / 0.0° | 离最近节点 155.2 m、离掩体 12.0 m |

根因是工具链的盲点：生成器**只压平节点核心**（半径 30 m 的圆盘），不压平出生区；
而校验器的出生区检查只看多边形**顶点**（四个角都在平地就通过）⇒ 内部是个 60° 的陡崖也照样 validate 全绿。

所以出生点现挑，判据全部来自既有口径（不新开数字），实现是纯逻辑可单测的
`systems/terrain/SpawnPicker.gd`：

- **双尺度坡度** ≤ `GameConfig.MAX_SLOPE_DEG`（12.8.5 ⑤）：step 8 m 与 4 m 都查。
  为什么要两个尺度 —— 1 灰度 ≈ 0.59 m 的量化台阶在 4 m 尺度上仍会造出假陡坡；
- **离掩体** ≥ **5 m**（点与遮挡体多边形的最短距离，点在楼里 = 0）；
- **离最近占领点** ≥ **100 m**（12.8.4「续航区在点外 100~200 m」），挑不出就 60 → 30 → 0 逐级放宽；
- 并列时依次比：step8 坡度 → step4 坡度 → 离掩体更远 → 离出生区边界更远（别贴着边界刷）；
- 挑不出（没地图 / 没 spawn_areas / 全区都陡）→ 退回 `MapGenerator.demo_spawn_point()`。

**谁用它**：玩家出生点与重生点、玩家那辆 IFV（锚点 + 35 m）、敌人（锚点 + demo 相对偏移）、
补给车队出发点 —— 四个都取自 `Main.spawn_anchor` 这一个字段（单一来源）。
敌人的**相对偏移不变**（出生点前方 45~75 m），只是每个偏移点再过一次「原地 15 m 内找平地」的微调：
第一版「出生 30 秒就能撞见敌人」的体验因此保住。

**登记待拍板**：敌人要不要按 RAAS 节点 / 东侧出生区分布（那是玩法改动，不是接线问题）。

**内容层的一个实测数字**：正式图的 `material.png` 经
`MapGenerator.terrain_zones_from_material_image()` 解析出 **205 片**区域
（泥 5 / 雪 139 / 草 61；雪与草是打点生成的，所以碎）。功能上没有问题（每片只是等面积圆），
但「雪」被打成 139 个圆饼在观感上是碎的 —— 要不要调大 `MATERIAL_MIN_CELLS`
或改成多边形表达，见第二节末尾那条待拍板。
